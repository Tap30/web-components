# Tapsi Design System — React

This Storybook covers the **React-rendered** packages of the workspace:

- **Theme** — `@tapsioss/theme`. Colour, typography and layout token galleries.
- **React UI** — `@tapsioss/react-ui`. React components built on
  [Base UI](https://base-ui.com).

`@tapsioss/web-components` and `@tapsioss/web-icons` are Lit-based and are
**not** here — Storybook supports exactly one renderer per instance, and those
packages have their own documentation at
[tap30.github.io/web-components](https://tap30.github.io/web-components). If
they ever need a sidebar, they arrive as a sibling `storybook/web-components/`
instance composed in through `refs`.

## Using the packages in an app

Three stylesheet imports, once, at the root of the app (`main.tsx`, `_app.tsx`
or the root `layout.tsx`). After that, components are used with no further
setup.

### 1. Tokens and a theme

`@tapsioss/theme` comes in two layers, and an app needs both: the **primitives**
(palette, font and number scales — the same for everyone), and **one theme** on
top of them, which is a product × mode pair.

```ts
import "@tapsioss/theme/tokens.css"; // primitives — always
import "@tapsioss/theme/ride/light.css"; // the theme to render in
```

The available themes are `ride/light`, `ride/dark`, `drive/light` and
`drive/dark`. The order of the two imports does not matter.

Importing a single theme needs nothing else: it applies to the whole page. To
switch themes at runtime, or to show more than one on a page, import each one
you need and pick with the `data-tapsi-theme` attribute — a subtree takes the
theme of its nearest ancestor that sets it:

```tsx
import "@tapsioss/theme/ride/light.css";
import "@tapsioss/theme/ride/dark.css";

<html data-tapsi-theme="ride-dark">
```

The same values are available to JavaScript, already resolved (`"0.5rem"`, not a
`var()`), for the cases CSS cannot reach:

```ts
import { tokens } from "@tapsioss/theme/ride/light";
```

**Still using the Lit components?** Apps on `@tapsioss/web-components` or
`@tapsioss/react-components` rely on the older tokens, which are named
`--tapsi-*`. The theme package still ships them, unchanged, and they share no
name with the current `--tds-*` tokens — so load both while you migrate one
component at a time, and drop this line when the last Lit component is gone:

```ts
import "@tapsioss/theme/legacy/tokens.css"; // replaces "@tapsioss/theme/css-variables"
```

### 2. Component styles

`@tapsioss/react-ui` ships all of its components' styles as one minified
stylesheet. Import it once, next to the theme:

```ts
import "@tapsioss/react-ui/styles.css";
```

The components do **not** import their own CSS — which is what lets the package
load in Node, in test runners and under server rendering without any CSS
configuration. So this line is required: without it, components render unstyled.
(And if they render in **magenta**, it is the theme that is missing — that is
the components' deliberate fallback for an undefined token.)

Put together, an app's entry file starts with:

```ts
import "@tapsioss/theme/tokens.css";
import "@tapsioss/theme/ride/light.css";
import "@tapsioss/react-ui/styles.css";
```

```tsx
import { Button } from "@tapsioss/react-ui";

<Button>دکمه تپسی</Button>;
```

This Storybook itself does not import `styles.css`: it runs the components from
source, where each one loads its own CSS module. See "How this resolves the
workspace" below.

## Conventions

**One story per component.** Every prop is exposed through the **Controls**
panel rather than frozen into separate stories, so variants, sizes and states
are explored by changing controls — not by clicking between sidebar entries. Add
a second story only when a component has something controls genuinely cannot
express: a multi-step flow, or a composition of several sub-components.

Give each prop an `argTypes` entry with a `description` and a `table.category`.
That is what turns the Controls panel into usable documentation instead of a
bare list, and `tags: ["autodocs"]` turns the same information into a generated
props table on the Docs tab.

**Sidebar grouping comes from a story's `title`, not its file location.**
Nothing enforces this, so it matters:

```ts
const meta = { title: "React UI/Button", component: Button };
```

One top-level segment per package: `Theme/…`, `React UI/…`.

**All stories live in this package**, one folder per workspace package it
documents (`src/react-ui/`, `src/theme/`). They import their subjects **by
package name** — `@tapsioss/react-ui`, not a relative path — so a story is a
real consumer, and a component missing from the package barrel breaks its story
straight away. It also keeps Storybook tooling out of the published packages.

## How this resolves the workspace

The root `tsconfig.json` maps `@tapsioss/*` to package **sources**, not `dist`:

```jsonc
"@tapsioss/theme/*": ["./packages/theme/src/*.ts"]
```

`.storybook/main.ts` registers `vite-tsconfig-paths` against that config, so
editing any package hot-reloads here. No build step, and nothing needs to be
published.

One caveat: for each token set, `tokens.css` and `tokens.ts` are **independent
artifacts** of the same Figma export, and neither is derived from the other.
Editing one will not move the other, so a token change means editing both — see
`packages/theme/AGENTS.md`. `packages/theme/scripts/check.ts` fails the build if
they disagree.

## Source of truth

**Figma** is authoritative for styles and token names.
**`@tapsioss/web-components`** is the reference for implementation decisions —
props, behaviour, accessibility and edge cases — as components are ported.
